# Task 34 AI trade market and persisted negotiation flow

Task 34 adds a pure AI trade evaluator/orchestrator, deterministic pair and package selection, persisted AI→player offers, and weekly integration through `DaySimulator` and Riverpod. AI↔AI packages are validated through `TradeService`, while AI→player offers use the existing `TradeOffer`/history collections and inbox actions. The change also adds counter limits, hard-reject pair reconstruction, NTC/R1/superteam preferences, and contract-dump buyer policy without changing `SaveSchema`. **Watch for:** **confirmed** weekly processing can skip a Sunday player-match boundary, **confirmed** AI↔AI execution bypasses counter and dump policy, and **confirmed** R1/deadline guardrails are incomplete on the player-offer path. **Verdict**: NEEDS_CHANGES

## High-level view

**confirmed** The AI↔AI loop deterministically samples pairs and packages but immediately accepts a mutually positive package, so the normal counter-round and seller-side dump policy do not govern that market.

**confirmed** AI→player offers persist and are routable, but a Sunday interactive match can skip the weekly hook and the offer builder does not apply the AI-only R1/veteran guardrails.

**confirmed** Existing serialized offer/history/NTC collections are reused without a `SaveSchema` change, but hard-reject cooldown reconstruction starts from offer creation rather than closure.

**confirmed** Contract-dump buyer probabilities exist, while the weekly executor omits the seller floor and deadline veteran-sale policy; the superteam brake also applies to all appetite, not only star acquisitions.

### AI↔AI weekly execution bypasses negotiation policy

**confirmed** `runWeeklyTick` evaluates packages, checks `AiTradePackage.isMutuallyBeneficial`, then calls `TradeService.createOffer` followed immediately by `acceptOffer` (`lib/core/ai/ai_trade_service.dart:571-606`). It never calls `evaluateOffer` or `respondToOffer` for the receiving AI. A package with both raw `surplusPct` values at least +2% is therefore an unconditional acceptance: threshold shifts, counter targets, round-specific hard rejects, and the seller-side contract-dump decision are not applied. Use one canonical AI response path, or make the direct package path enforce every policy it replaces.

### Counter-round hard-reject probabilities are configured but unused

**confirmed** `AiBalance` exposes 0%/15%/35% hard-reject probabilities for counter rounds 1/2/3 (`lib/core/balance/ai_balance.dart:210-212`), but `evaluateOffer` uses the same surplus-band probabilities for every round and only forces a hard reject when `round > tradeMaxCounters` (`lib/core/ai/ai_trade_service.dart:218-291`). A persisted AI/player thread does not implement the documented increasing chance of ending at rounds 2 and 3. Apply the round-specific roll before building a counter and test all three deterministic cases.

### Counter construction can go below the +2% floor

**confirmed** `buildCounterProposal` chooses the closest legal candidate at or above the target, but if none exists it falls back to the highest `bestBelow` candidate (`lib/core/ai/ai_trade_service.dart:386-414`). `respondToOffer` persists that candidate without checking `tradeOfferMinimum` (`lib/core/ai/ai_trade_service.dart:487-515`). A counter can therefore be below the documented minimum +2%; when no legal package reaches the floor, the response should reject/end the thread instead.

### Hard-reject pair cooldown starts at offer creation

**confirmed** `isPairTradeBlocked` reconstructs the block as `entry date + 30 days` (`lib/core/services/trade_service.dart:219-237`). For offer threads, `_closeTradeOffer` records history through `_addOfferHistory`, which copies `offer.seasonYear/week/day` rather than the current league date (`lib/core/services/trade_service.dart:1973-2010,2016-2043`). A delayed hard reject consequently receives only the remainder of the 30-day block. Record closure date in the existing history fields; no new save field is needed.

### Sunday interactive matches skip the weekly trade tick

**confirmed** `DaySimulator.simulateDay` returns immediately when `_resolveRound` finds the player fixture (`lib/core/services/day_simulator.dart:185-199`), while the new AI trade call is only in the later `day == 7` boundary block (`lib/core/services/day_simulator.dart:336-348`). `matchDaysForWeek` can select Sunday as the weekend match day (`lib/core/services/schedule_generator.dart:94-103`), and `GameController.applyPlayerMatchResult` advances the date without running the weekly block. On those weeks neither AI↔AI trades nor AI→player offers are generated. Move weekly boundary processing into shared post-match finalization or catch it up after a Sunday result with an idempotence guard.

### AI→player offers bypass the R1 and veteran guardrails

**confirmed** `_runPlayerOffers` calls `_buildPlayerOffer`, which validates legality and AI surplus but never calls `_violatesAiGuardrails` (`lib/core/ai/ai_trade_service.dart:626-679`). The pick loop can select any owned pick (`lib/core/ai/ai_trade_service.dart:731-779`), including a first-round pick, and the target loop does not reject a 30+ player for a `rebuild`/`retool` team. The guardrail is only applied to the AI↔AI package loop (`lib/core/ai/ai_trade_service.dart:579-581`). Run all AI-originated proposals through the same guardrail gate before persisting an offer.

### The R1 limit is not a rolling three-year guardrail

**confirmed** `_violatesFirstRoundLimit` counts accepted R1 picks only from `currentSeason.year` through `currentSeason.year + 2` (`lib/core/ai/ai_trade_service.dart:1182-1205`). It ignores the two preceding years, so a team that already sent R1 picks in Y−2 and Y−1 can send another in Y without tripping the claimed maximum of two in any three consecutive years. Check the windows containing each outgoing pick year, not just a window anchored at the current season.

### Contract dumps can bypass the dumper’s negative-surplus table

**confirmed** The documented −10%/−25%/−40% seller floor is implemented only inside `evaluateOffer` via `_dumpFloor` (`lib/core/ai/ai_trade_service.dart:191-194,1275-1284`). The AI↔AI weekly loop instead accepts any package for which `contractDump && buyerAcceptsContract` is true (`lib/core/ai/ai_trade_models.dart:65-72` and `lib/core/ai/ai_trade_service.dart:579-580`), regardless of the dumper’s surplus. A toxic contract can therefore execute below −40% or with a package the seller-side policy would reject. Enforce the dumper’s effective surplus and first-round conditions before treating buyer acceptance as sufficient.

### Deadline contract-sale policy is not wired

**confirmed** `tradeVeteranSaleProbability = 0.45` and `tradeDeadlinePickBump = 10.0` are defined in balance but have no use in the Task 34 implementation (`lib/core/balance/ai_balance.dart:223-230`). `_contractDumpProposals` selects burden players without restricting the deadline sale to `rebuild`/`retool`, age 30+, expiring contracts, or applying the 45% roll (`lib/core/ai/ai_trade_service.dart:924-974`). The deadline market therefore does not implement the documented veteran-sale behavior; wire the condition and deterministic roll, or remove the claim from the acceptance criteria.

### Superteam brake is broader than the documented star-acquisition rule

**confirmed caveat** `appetiteForTeam` halves the entire appetite whenever `teamPower > league average + 12` (`lib/core/ai/ai_trade_service.dart:86-92,1408-1430`). It has no target/star context, and `tradeSuperteamStarOverall` is unused. This suppresses selling, contract dumps, and non-star depth trades as well as star additions. If the canonical behavior is the documented “adding stars” brake, make the appetite decision target-aware; if the intended Task 34 rule is a general brake, make the broader behavior explicit and test it.

### Initial AI→player offers do not target the +10% anchor

**confirmed caveat** The player-offer builder accepts the first legal package whose evaluated surplus is between +2% and `tradeOfferTarget + 18%` (`lib/core/ai/ai_trade_service.dart:731-779`). It never selects the package closest to the configured +10% opening target; +2% is used as the opening lower bound rather than only as the post-counter floor. This can produce opening offers at the minimum instead of the documented +10% anchor. Select by distance to the target and reserve the +2% bound for later counters.

### Coverage does not exercise the integration risks

**confirmed** The new Task 34 tests cover replayable package salt, one persisted AI response, a manual three-counter cap, and the outside-window no-op (`test/task34_ai_trade_test.dart:24-179`). They do not run a real weekly AI↔AI execution, persist/reload an AI→player pending offer and counter, simulate a Sunday player match, test a rolling R1 window, or assert contract-dump floors/deadline policy. Add those cases before relying on the passing focused suite as evidence for the Task 34 acceptance criteria.
