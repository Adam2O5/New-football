## Znalezione błędy

### B1 — Bramki obronione bramkarza liczone z jego goli, a test nagród jest wyłączony

- **Lokalizacja:** `lib/core/services/season_awards.dart:565-589`, ujawnione przez `test/calendar/task39_season_service_test.dart:261-303`
- **Waga:** high
- **Opis:** `_AwardStats.goalsPrevented` to `shotsFaced - goals` (gole strzelone przez tego zawodnika), a nie gole stracone przez drużynę, gdy bramkarz był na boisku. Komentarz przy klasie sam nazywa to protezą. Wynik wchodzi do oceny najlepszego bramkarza (`_bestGoalkeeper`, wagi `gkGoalsPreventedWeight`). Dwóch bramkarzy z tym samym `shotsFaced` i zerową liczbą goli dostaje identyczne „gole obronione”, niezależnie od tego, ile puścili. Test „computes award leaders from player stats and is idempotent” ma `skip:` z opisem, że stare fixture już nie wygrywa. CI zostaje zielone, a `test/balance/gameplay_rules_test.dart:50-111` sprawdza tylko próg minut na dwuosobowej kadrze, nie składnik goli obronionych.
- **Propozycja:** nie trzymaj regresji na `skip:`. Albo przywróć akumulator goli straconych i test, albo wyłącz składnik z oceny, dopóki akumulatora nie ma, i zastąp pominięty test asercją, która opisuje dzisiejszy kontrakt.

```dart
// season_awards.dart — docelowo, gdy sezon zbiera gole stracone na boisku
goalsPrevented = max(0, stats.shotsFaced - stats.goalsConcededWhileOnPitch);

// task39 — zamiast skip: na całym teście
test('best GK prefers fewer goals conceded at the same shots faced', () {
  // dwóch GK, ten sam shotsFaced i rating, różna liczba goli straconych
  expect(awards.bestGkPlayerId, betterGk.id);
});
```

### B2 — Identyfikator serii play-off jest losowym UUID i psuje seed dogrywki

- **Lokalizacja:** `lib/core/services/season_service.dart:190-195`, konsumowane w `lib/core/services/season_post_match.dart:196` (`matchSeed(..., '$matchId:tiebreak')`). Powiązane: `test/data/initial_roster_replay_test.dart:29-30`
- **Waga:** high
- **Opis:** `_series` nadaje `id: _uuid.v4()`. Identyfikator meczu to `playoff:${series.id}:${n}`. Remisowy tie-break (`Random(matchSeed(saveSeed, seasonYear, '$matchId:tiebreak'))`) zależy więc od UUID, nie tylko od `saveSeed`. Dwa wejścia w play-off z tym samym ziarnem dają inne dogrywki, karne i potencjalnie innego mistrza. Zapis po wygenerowaniu drabinki jest stabilny (UUID ląduje w JSON), ale odtworzenie sezonu od stanu sprzed play-offów już nie. Test powtórki nowej kariery wprost wyłącza UUID z porównania, więc tej dziury nie widzi. `test/calendar/season_randomness_test.dart` pinuje loterię i emerytury, nie puchar.
- **Propozycja:** identyfikator serii wyprowadzać z roku, konferencji, rundy i obu drużyn. UUID zostawić dla identyfikatora zapisu (`GameFactory`, `game_factory.dart:116`) i wiadomości.

```dart
PlayoffSeries _series(
  String high,
  String low, {
  required String id,
}) => PlayoffSeries(
  id: id, // np. '2026:europe:qf:1:$high:$low'
  higherSeedTeamId: high,
  lowerSeedTeamId: low,
  winsNeeded: 3,
);
```

Test: dwa razy `generatePostseasonFixtures` na tym samym stanie i `saveSeed`, potem porównanie `playoffBrackets` oraz wyniku meczu 0:0 po `_resolvePostseasonTiebreak`.

### B3 — Tie-break tabeli, loterii i draftu nie jest porządkiem całkowitym

- **Lokalizacja:** `lib/core/models/standing.dart:65-76`, `lib/core/services/draft_service.dart:84-88`, `lib/core/services/season_lottery.dart:34-38`. Kontrast: `lib/core/services/season_awards.dart:472-479` (trener roku dokłada bramki i `teamId`)
- **Waga:** high
- **Opis:** `ConferenceStandings.sorted` oraz sort loterii/draftu porównują tylko punkty i różnicę bramek. Przy równych punktach i równej różnicy kolejność zależy od aktualnego układu listy. `List.sort` w Dart nie gwarantuje stabilności. Play-off bierze nasiona z `.sorted` (`season_playoffs.dart:6-21`), a draft układa drużyny spoza loterii z tego samego klucza. Test `test/market/draft_order_test.dart:57` nazywa przypadek „tied standings”, ale fixture (`:37-41`) daje różne `goalsFor` przy `goalsAgainst == 0`, więc różnica bramek remisu nie dotyka. Brak testu równych punktów i równej różnicy.
- **Propozycja:** jeden komparator, użyty przez tabelę, loterię i draft. Dla tabeli (lepszy wyżej): punkty, różnica, bramki zdobyte, `teamId`. Dla loterii odwrócić kierunek, zostawić ten sam ostatni klucz.

```dart
int compareStandings(Standing a, Standing b) {
  final points = b.points.compareTo(a.points);
  if (points != 0) return points;
  final difference = b.goalDifference.compareTo(a.goalDifference);
  if (difference != 0) return difference;
  final goals = b.goalsFor.compareTo(a.goalsFor);
  if (goals != 0) return goals;
  return a.teamId.compareTo(b.teamId);
}
```

Test: dwie drużyny 10 pkt, różnica 0, różne `goalsFor`; osobno obie z identycznym bilansem — oczekiwany `teamId` rosnąco i stabilny `conferenceRank`.

### B4 — Remis bez `winnerTeamId` dopisuje zwycięstwo niżej rozstawionemu

- **Lokalizacja:** `lib/core/models/match_models.dart:256-266`
- **Waga:** medium

- **Propozycja:** remis bez zwycięzcy ma nie zmieniać stanu serii (albo rzucać). Test jednostkowy na 1:1 oraz na karne 0:0 z `winnerTeamId` niżej rozstawionego.

```dart
if (resolvedWinner == null && result.homeGoals == result.awayGoals) {
  throw StateError('Postseason game $id is still a draw');

```

## Rekomendowane kolejne kroki

1. **Tie-break i identyfikatory serii (B2, B3, G1).** Najpierw stabilne id serii i wspólny komparator tabeli. Potem test drabinki na sztucznym wyniku, zdjęty z blacklisty, bez ruszania silnika meczowego. To zamyka mistrza, dogrywkę i draft spoza loterii.
2. **Nagrody (B1, S2).** Zdjąć `skip:`. Albo naprawić gole obronione i przywrócić zwycięzców, albo zastąpić test jawnym kontraktem protezy, żeby CI znowu pilnowało składników oceny.
3. **Statystyki sezonu (B6, G3).** Jeden test agregacji dwóch meczów, zanim ruszy się formuła MVP.
4. **Terminarz (G4).** Dodać asercje par i boisk do istniejącego pliku. Mały diff, duży zysk przy zmianie circle method.
5. **Silnik (G2).** Nowy, krótki plik na `SimulationMatchEngine`, nie reanimacja `MatchEngine`. Osobna decyzja, które `deferredCases` AI (draft, transfer, kadra) wracają — czarna lista ma być listą konkretnych przypadków, nie workiem „AI or match-engine”.
6. **Cap (B7, G6, S3).** Test granicy progu i kwot na `FinanceScreen`. Heurystykę `_thresholds` ruszać dopiero z testem macierzy default kontra wstrzyknięty balans.
7. **Porządki nazw (S1, S5).** Przy najbliższej edycji polityk urgent-message scalić pliki i ujednolicić tag `property`. Nie robić z tego osobnego, szerokiego PR-a.

Świadomie nie proponuję włączenia 17 plików `*_long.dart` do CI: profil jest oznaczony jako ręczny, a część to benchmarki. Warto raz na jakiś czas odpalić `scripts/test.ps1 -Profile long` lokalnie i zapisać, które pliki jeszcze kompilują się po zmianie API.
